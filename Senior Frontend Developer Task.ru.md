# Задание для старшего frontend-разработчика

## Финтех-панель с данными в реальном времени

Создайте небольшое Angular-приложение с двумя страницами: **панелью рыночных данных в реальном времени** и **настройками генератора данных**.

Реализуйте библиотеку WebAssembly, которая генерирует имитационные финансовые данные и работает внутри Web Worker. Предыдущий опыт в финтехе не требуется: необходимые определения и примеры приведены ниже.

**Обязательно:** Angular, TypeScript, самостоятельно написанная кандидатом библиотека Wasm, Web Worker и модульные тесты. **Язык и инструменты для разработки Wasm выберите самостоятельно.** Вспомогательные библиотеки — на ваше усмотрение.

Использование ИИ разрешено. Вы должны понимать свою реализацию, протестировать её и уметь объяснить, как она работает.

## 1. Страница панели рыночных данных

Отобразите таблицу, обновляемую в реальном времени, с одной строкой для каждого вымышленного финансового инструмента. Инструмент — это просто актив, обозначенный символом, например `ALFA` или `BETA`.

Для каждого инструмента отображайте следующие пять показателей:

| Показатель | Значение и способ расчёта |
|---|---|
| Цена последней сделки | Цена последней сгенерированной сделки по инструменту. |
| Спред между ценами покупки и продажи (bid–ask) | `askPrice − bidPrice`. Bid — цена доступной заявки на покупку; ask — цена доступной заявки на продажу. |
| Объём торгов | Сумма количества единиц во всех сгенерированных сделках по этому инструменту с начала текущего запуска. |
| Средневзвешенная по объёму цена (VWAP) | `sum(tradePrice × tradeQuantity) / sum(tradeQuantity)` с начала текущего запуска. Более крупные сделки вносят больший вклад. |
| Дисбаланс биржевого стакана | `(bidQuantity − askQuantity) / (bidQuantity + askQuantity)`, с использованием последних доступных объёмов заявок на покупку и продажу. |

Рассчитывайте объём и VWAP накопительно, **без скользящих временных окон**. Учитывайте каждую сделку ровно один раз; доступные объёмы заявок bid/ask не входят в объём торгов.

До поступления данных отображайте показатели как недоступные, а объём — как нулевой. Если знаменатель формулы равен нулю, отображайте значение как недоступное. Цены выводите в денежном формате, а дисбаланс — как число от −1 до +1.

Добавьте элемент управления **«Пауза / Возобновить»** и простой индикатор состояния генератора. Пауза останавливает генерацию; возобновление сохраняет текущие значения и накопленные итоги, при этом данные за время паузы не генерируются.

### Пример расчёта

По инструменту поступили две сделки: 10 единиц по $100 и 30 единиц по $102.

- Цена последней сделки: **$102**.
- Объём: **40 единиц**.
- VWAP: `(100 × 10 + 102 × 30) / 40 = $101.50`.

При текущей цене bid $101.96 и цене ask $102 спред составляет **$0.04**. При объёме заявок bid 600 и объёме заявок ask 400 дисбаланс равен `(600 − 400) / (600 + 400) = 0.20`.

## 2. Страница настроек

Создайте форму с валидацией для трёх настроек генератора:

| Настройка | Значение | По умолчанию | Допустимый диапазон |
|---|---|---:|---:|
| Количество инструментов | Количество вымышленных инструментов, для которых генерируются данные. | 5 | 1–50 |
| Количество обновлений в пакете | Общее количество рыночных обновлений в каждом сгенерированном пакете. | 100 | 1–1 000 |
| Интервал между пакетами | Заданный интервал между пакетами в миллисекундах. | 500 | 50–2 000 |

Все настройки должны быть целыми числами. Например, 100 обновлений каждые 500 мс дают номинальную скорость **200 обновлений в секунду суммарно по всем инструментам**, а не по каждому инструменту. Один инструмент может встречаться в пакете несколько раз.

Редактирование формы не должно сразу влиять на генератор. Действие **«Применить»** начинает новый запуск с новыми настройками и очищает значения и накопленные итоги предыдущего запуска. Оно также запускает генерацию, если предыдущий запуск был приостановлен.

Приложение запускается с настройками по умолчанию. Переходы между страницами должны сохранять активный запуск и его состояние — работа или пауза. Навигация не должна создавать дополнительные генераторы. Результаты предыдущего запуска не должны перезаписывать состояние нового запуска.

Сохранять настройки после перезагрузки страницы браузера не требуется.

## 3. Генератор Wasm и Web Worker

Библиотека Wasm должна генерировать **рыночные обновления**, а не независимо рандомизированные показатели панели. Каждое обновление представляет одну имитационную сделку и текущий снимок заявок bid/ask.

Пример обновления:

```json
{
  "instrument": "ALFA",
  "priceCents": 10200,
  "tradeQuantity": 30,
  "bidCents": 10196,
  "askCents": 10200,
  "bidQuantity": 600,
  "askQuantity": 400
}
```

Здесь `10200` означает $102.00. Этот JSON описывает необходимую информацию; вы можете выбрать другой формат передачи данных.

Генератор должен сохранять состояние каждого инструмента между вызовами и возвращать пакеты запрошенного размера. Цены должны изменяться на основе предыдущих значений, а не быть полностью независимыми при каждом обновлении. Цены должны оставаться положительными, bid — быть ниже ask, количество единиц в сделке — положительным, а объёмы заявок в стакане — неотрицательными. В этой упрощённой модели в качестве цены каждой сделки выбирайте bid или ask из соответствующего обновления.

Генерация случайных значений и логика формирования цен должны действительно выполняться в Wasm. Генератора на TypeScript, обёрнутого в тривиальный вызов Wasm, недостаточно. Реалистичная модель биржи или алгоритм сопоставления заявок не требуются.

Загружайте и выполняйте генератор Wasm в Web Worker. Вы самостоятельно решаете, где рассчитываются показатели и как данные передаются между Wasm, Web Worker и Angular.

Для сгенерированных цен используйте целое количество центов, а рассчитанные цены округляйте только для отображения. Не храните полную историю событий. Интерфейс может обновляться реже, чем генерируются данные, но каждая сгенерированная сделка должна учитываться в объёме и VWAP.

При увеличении скорости генерации интерфейс должен оставаться удобным для использования. Отображайте понятные ошибки инициализации и освобождайте ресурсы генератора при его замене или когда они больше не нужны. Формальный отчёт о тестировании производительности не требуется.

## 4. Модульные тесты — обязательны

Добавьте содержательные модульные тесты для следующих аспектов:

- Расчёт показателей, включая приведённый пример, нулевые знаменатели и независимость данных разных инструментов.
- Валидация настроек и сброс состояния при их применении.
- Поведение при паузе и возобновлении, а также отклонение результатов предыдущего запуска.
- Поведение генератора, включая соответствие запрошенным размерам пакетов и корректность сгенерированных значений.

Для тестов генератора можно использовать тестовый фреймворк выбранного исходного языка или выполнять скомпилированный модуль Wasm. При необходимости используйте фиксированные входные данные или управляемые зависимости; тесты не должны зависеть от длительного ожидания в реальном времени.

Сквозные тесты (end-to-end) не требуются.

## 5. Сдача задания и развёртывание

1. **Создайте репозиторий на GitHub.** Включите Angular-приложение, исходный код Wasm, тесты и README с инструкциями по сборке, запуску и тестированию. Рекомендуется сохранить историю коммитов разработки, а не загружать только итоговую версию.
2. **Настройте автоматическое развёртывание.** Подключите репозиторий к выбранному хостингу, например Cloudflare Pages, GitHub Pages или Vercel. Можно использовать бесплатный хостинг или уже имеющийся платный сервис. Каждый push в репозиторий должен автоматически запускать сборку и повторное развёртывание приложения без ручных действий.
3. **Предоставьте ссылки на репозиторий и работающую демоверсию.** Убедитесь, что обе доступны интервьюерам.
4. **Будьте готовы обсуждать и изменять реализацию.** На собеседовании мы обсудим ваши архитектурные решения и можем попросить изменить или расширить часть приложения. **Автоматическое развёртывание обязательно**, чтобы изменения, отправленные в репозиторий во время собеседования, появлялись в демоверсии без ручного развёртывания.
