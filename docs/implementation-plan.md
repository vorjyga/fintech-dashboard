# План реализации Fintech Dashboard

## 1. Цель и принятые решения

Реализовать приложение по английскому оригиналу `Senior Frontend Developer Task.docx`: две страницы Angular, самостоятельно написанный генератор рыночных обновлений в WebAssembly, выполнение в Web Worker, модульные тесты и автоматическое развёртывание демоверсии.

Исходное состояние: в репозитории находятся оригинал ТЗ, русский перевод и README. Репозиторий `vorjyga/fintech-dashboard` публичный, основная ветка — `main`.

### Стек

| Область | Решение |
|---|---|
| Приложение | Angular 21 LTS, standalone-компоненты, строгая типизация |
| Окружение | Node.js 22.13.1, npm, package-lock.json |

| Состояние Angular | Корневой сервис с Signals, компоненты с OnPush |

Конкретные версии зависимостей фиксируются в lock-файле при создании проекта. Angular 21 совместим с установленным Node.js 22.13.1: https://angular.dev/reference/versions.

ТЗ не задаёт тему оформления. Angular Material, Tailwind и светлая тема выбраны для реализации по согласованию с пользователем. По согласованию автоматический деплой выполняется при push в `main`; это уточняет формулировку оригинального ТЗ о деплое при каждом push в репозиторий.

SSR не подключается в первой версии: данные генерируются в браузере, а демо размещается как статическое приложение на GitHub Pages. Это архитектурное упрощение, а не запрет или требование английского ТЗ.

В первую версию не входят backend, авторизация, реальные рыночные данные, графики, история сделок, сохранение настроек после перезагрузки, мультиязычность и реалистичный алгоритм сопоставления заявок.

### Правила совместного использования Angular Material и Tailwind

Material даёт готовые компоненты интерфейса, а Tailwind упрощает вёрстку страниц. Отключение Preflight уменьшает влияние глобального сброса Tailwind на оформление Material. Tailwind 4 не рассчитан на обработку через Sass, поэтому стили Tailwind и тему Material хранить в отдельных файлах.

1. Использовать Material для таблицы, полей формы, кнопок, индикаторов и сообщений об ошибках.
2. Использовать Tailwind для сетки страницы, flex/grid, внешних отступов, размеров контейнеров и адаптивности. Классы раскладки преимущественно применять к собственным контейнерам вокруг Material-компонентов.
3. Настраивать цвета, типографику и плотность Material через официальный API темы и overrides. Не переопределять внутренние `.mat-*` и `.mdc-*` селекторы, не использовать `::ng-deep` и массовый `!important` для оформления компонентов.
4. Отключить Tailwind Preflight: подключать только `tailwindcss/theme.css` и `tailwindcss/utilities.css` в соответствующих CSS layers, без импорта `tailwindcss/preflight.css` и без общего `@import "tailwindcss"`.
5. Держать Tailwind в отдельном глобальном `.css`-файле, а тему Material — в отдельном `.scss`-файле. Не импортировать Tailwind в Sass и не применять его директивы через Sass.
6. Подключить `tailwindcss`, `@tailwindcss/postcss` и `postcss`, настроить плагин в корневом `.postcssrc.json`. Оба файла глобальных стилей включить в сборку Angular.
7. Цвета собственных блоков согласовать с системными токенами Material. Не создавать независимую палитру Tailwind для элементов, которые должны соответствовать теме приложения.
8. В шаблонах использовать полные имена utility-классов. Для условных вариантов выбирать из статически перечисленных классов, чтобы production-сборка включала нужные стили.
9. При проверке интерфейса убедиться, что Tailwind не меняет внутренние отступы, размеры и focus-состояния Material-компонентов.

Документация:

- Tailwind с Angular: https://tailwindcss.com/docs/installation/framework-guides/angular.
- Отключение Preflight: https://tailwindcss.com/docs/preflight.
- Tailwind и Sass: https://tailwindcss.com/docs/compatibility.
- Темизация Angular Material 21: https://github.com/angular/components/blob/21.0.0/guides/theming.md.

## 2. Архитектура и контракты

### 2.1. Поток данных

```text
Settings page
    │ Apply / валидированные настройки
    ▼
Корневой сервис Angular
    │ Команды управления с runId
    ▼
Web Worker
    ├── Загружает Wasm
    ├── Управляет расписанием генерации
    ├── Получает пакеты рыночных обновлений
    ├── Учитывает каждую сделку в накопительных показателях
    └── Передаёт снимки таблицы в Angular
              ▲
              │
      AssemblyScript → Wasm
      состояние инструментов + PRNG + генерация цен
```

Angular получает снимки показателей всех инструментов. Отдельные сделки обрабатываются внутри Worker. Переходы между страницами сохраняют производителя; жизненным циклом управляет сервис на уровне приложения.

Для асинхронных потоков данных обязательно использовать RxJS. Сообщения Worker (снимки, статусы и ошибки) представлять как типизированные `Observable`, а внутренние источники событий при необходимости реализовывать через `Subject`. Наружу предоставлять только `Observable`, не открывая возможность вызывать `next` из компонентов. Проверку `runId`, `sequence` и `commandId` выполнять до обновления состояния. Signals использовать для текущего состояния, отображаемого компонентами; не создавать параллельное хранилище того же состояния в Subjects. При замене Worker и уничтожении приложения завершать подписки и снимать обработчики событий.

### 2.2. Настройки

```ts
interface ProducerSettings {
  instrumentCount: number;
  updatesPerBatch: number;
  batchIntervalMs: number;
}
```

| Поле | По умолчанию | Ограничения |
|---|---:|---|
| instrumentCount | 5 | Целое число от 1 до 50 |
| updatesPerBatch | 100 | Целое число от 1 до 1000 |
| batchIntervalMs | 500 | Целое число от 50 до 2000 |

Общую функцию валидации использовать в форме и сервисе. Worker проверяет полученные настройки перед запуском.

Номинальная скорость: `updatesPerBatch × 1000 / batchIntervalMs`. Это скорость суммарно по всем инструментам. Максимальная конфигурация — 20 000 обновлений в секунду.

### 2.3. Рыночное обновление

```ts
interface MarketUpdate {
  instrumentId: number;
  priceCents: number;
  tradeQuantity: number;
  bidCents: number;
  askCents: number;
  bidQuantity: number;
  askQuantity: number;
}
```

Все значения целочисленные. `instrumentId` находится в диапазоне от `0` до `instrumentCount - 1`.

Стабильные символы: первые пять — `ALFA`, `BETA`, `GAMMA`, `DELTA`, `EPSILON`; остальные — `INST006` … `INST050`.

### 2.4. Интерфейс Wasm

Использовать числовой ABI без передачи строк и объектов.

| Экспорт | Назначение |
|---|---|
| abiVersion(): i32 | Версия контракта, первоначально 1 |
| init(instrumentCount: i32, seed: u32): i32 | Инициализация состояния; 0 означает успех |
| generateBatch(size: i32): usize | Генерация пакета; возвращает адрес данных |
| getBatchLength(): i32 | Количество записей последнего пакета |
| memory | Экспортированная линейная память |

При недопустимых параметрах `init` возвращает ненулевой код. При недопустимом размере пакета `generateBatch` возвращает `0`, а длина пакета становится нулевой; состояние цен не изменяется.

Запись занимает семь `u32`, или 28 байт, в порядке полей `MarketUpdate`. Буфер заранее выделяется для 1000 записей и переиспользуется. Worker обрабатывает его до следующего вызова генератора и не передаёт память Wasm в Angular.

Использовать статическую память AssemblyScript через `memory.data`, чтение и запись через `load` и `store`. Документация: https://www.assemblyscript.org/stdlib/globals.html.

### 2.5. Снимок показателей

```ts
interface InstrumentSnapshot {
  instrumentId: number;
  symbol: string;
  lastPriceCents: number | null;
  spreadCents: number | null;
  volume: bigint;
  vwap: {
    numeratorCents: bigint;
    denominator: bigint;
  } | null;
  imbalance: number | null;
}
```

Объём и сумма `priceCents × tradeQuantity` накапливаются как `bigint`, чтобы длительная работа сохраняла точность целых чисел. Для VWAP сохраняется точное отношение; округление выполняется только при отображении.

Передавать снимки через `postMessage`, без JSON-сериализации. Structured clone поддерживает `bigint`: https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm.

### 2.6. Команды и события Worker

Команды:

- `start`: runId, настройки, seed, абсолютный URL Wasm.
- `pause`: runId, commandId.
- `resume`: runId, commandId.

События:

- `ready`: runId, версия ABI.
- `snapshot`: runId, возрастающий sequence, массив строк.
- `status`: runId, commandId для подтверждения команды, состояние running или paused.
- `error`: runId, этап ошибки и понятное сообщение.

Оформить варианты как discriminated unions. Сервис принимает события только от активного `runId`. Снимки с уже обработанным или меньшим `sequence` игнорируются. Подтверждения управления сверяются с `commandId`.

### Этап 2. Проверить интеграцию Wasm

Статус: выполнен 2026-10-06. Проверки и границы реализации: [отчёт этапа 2](stage-2-report.md).

4. Создать Worker штатным способом Angular CLI.

### Этап 3. Генератор рынка в AssemblyScript

Зависимость: этап 2.

1. Реализовать PRNG xorshift32 непосредственно в AssemblyScript. Нулевой seed заменять фиксированным ненулевым значением.
2. Сохранять состояние PRNG и предыдущую цену каждого инструмента между вызовами.
3. Начальные цены bid установить как `10000 + instrumentId × 1000` центов.
4. Для каждого обновления выбирать инструмент внутри Wasm; повторения в пакете разрешены.
5. Изменять предыдущий bid на случайную величину от −5 до +5 центов.
6. Ограничить bid диапазоном от 1 до 1 000 000 центов.
7. Установить ask выше bid на случайное число от 1 до 20 центов.
8. Выбирать цену сделки равной bid или ask текущего обновления.
9. Генерировать trade quantity от 1 до 1000, объёмы bid/ask — от 0 до 10 000.
10. Возвращать ровно запрошенное количество записей в переиспользуемом буфере.
11. При init полностью сбрасывать состояние генератора.

Seed создаётся для нового запуска в Worker; все последующие случайные числа и решения о ценах вычисляются в Wasm. В тестах используется фиксированный seed. Указанные диапазоны — выбранная модель симуляции.

Критерий готовности: тесты скомпилированного Wasm подтверждают размеры пакетов, допустимость значений, воспроизводимость и продолжение состояния между вызовами.

### Этап 4. Накопление и расчёт показателей

Зависимость: общие контракты этапа 1; интеграция с генератором после этапа 3.

1. Создать чистый модуль агрегирования без зависимостей от Angular и глобального Worker API.
2. Хранить для каждого инструмента последнюю сделку, последний bid/ask, последние объёмы заявок, накопленный объём и накопленную стоимость сделок.
3. Каждую сделку учитывать один раз: объём увеличивать на tradeQuantity, стоимость — на `BigInt(priceCents) × BigInt(tradeQuantity)`.
4. Рассчитывать спред по последнему снимку bid/ask.
5. Рассчитывать дисбаланс как `(bidQuantity − askQuantity) / (bidQuantity + askQuantity)`.
6. При нулевом знаменателе возвращать null.
7. До первой сделки возвращать null для недоступных показателей и 0n для объёма.
8. Не сохранять обработанные сделки и старые пакеты.
9. Выводить цены в USD с двумя знаками после запятой. VWAP округлять до ближайшего целого цента только при отображении; половину цента округлять вверх.
10. Дисбаланс отображать с двумя знаками, сохраняя значение в диапазоне −1 … +1.

Критерий готовности: пример ТЗ даёт последнюю цену $102.00, объём 40, VWAP $101.50, спред $0.04 и дисбаланс 0.20. Инструменты независимы.

### Этап 5. Worker и расписание генерации

Зависимости: этапы 3 и 4.

1. Выделить тестируемый контроллер с внедряемыми часами, таймерами, генератором и отправкой событий.
2. После start загрузить Wasm, инициализировать генератор и агрегаторы, отправить пустой снимок и состояние running.
3. Первый пакет генерировать через заданный интервал.
4. Использовать один последовательный цикл setTimeout. Следующий вызов назначать после завершения текущего пакета; пропущенные интервалы не догонять.
5. Полностью обработать пакет до переиспользования памяти Wasm.
6. Обычные снимки отправлять не чаще одного раза в 100 мс; все промежуточные сделки учитывать.
7. При pause отменить следующий таймер, отправить окончательный снимок и подтвердить paused.
8. При resume продолжить тот же Wasm и агрегаторы; следующий пакет создать через полный интервал.
9. Не генерировать сделки за время паузы.
10. При ошибке остановить расписание и отправить error.
11. Обработать ошибки загрузки, компиляции, несовместимости ABI и выполнения генератора.

Критерий готовности: на искусственных часах работают генерация, пауза, возобновление и ограничение частоты снимков. Итоги учитывают все сделки.

### Этап 6. Сервис управления запусками

Зависимость: этап 5.

1. Создать singleton-сервис с readonly Signals для строк, активных настроек, статуса и ошибки.
   Потоки сообщений Worker организовать через RxJS `Observable`; внутренние события при необходимости — через закрытые `Subject`. Принятые события обновляют Signals. Освобождение подписок и обработчиков привязать к жизненному циклу активного Worker и сервиса.
2. Один раз запускать значения по умолчанию из корневого компонента.
3. Ввести состояния initializing, running, pausing, paused, resuming и error.
4. Во время подтверждения Pause/Resume блокировать повторную команду соответствующей кнопки.
5. Перед Apply валидировать настройки. Невалидные значения не изменяют активный запуск.
6. При допустимом Apply увеличить runId, отключить обработчики и завершить старый Worker, очистить значения, сохранить настройки и создать новый Worker.
7. Применение неизменённых настроек также начинает новый запуск со сбросом.
8. Apply после паузы автоматически запускает генерацию.
9. Игнорировать сообщения и завершения асинхронной инициализации старого запуска.
10. При error сохранить последние отображённые значения, завершить Worker и показать Retry.
11. Retry начинает новый запуск с последними применёнными настройками и очищает итоги.
12. При уничтожении приложения освобождать Worker и обработчики.

Фабрику Worker внедрять для тестирования сервиса без настоящего браузерного Worker.

Критерий готовности: не больше одного активного производителя, навигация сохраняет состояние, Apply отделяет новый запуск от старого.

### Этап 7. Dashboard

Зависимость: этап 6. Представление можно готовить раньше на согласованных тестовых снимках.

1. Добавить навигацию Dashboard / Settings.

### Этап 8. Страница настроек

Критерий готовности: изменения действуют только после Apply; применение очищает итоги и запускает производителя независимо от прежнего состояния.

## 4. Обязательный набор тестов

| Область | Сценарии |
|---|---|
| Wasm | Размеры пакетов 1, 100, 1000; недопустимые размеры; границы количества инструментов |
| Значения генератора | Положительные цены и trade quantity; bid < ask; неотрицательные book quantities; цена сделки равна bid или ask |
| Состояние генератора | Воспроизводимый seed; продолжение состояния между пакетами; сброс при init |
| Непрерывность цены | Изменение bid одного инструмента соответствует выбранному шагу |
| Метрики | Пример ТЗ; несколько инструментов; повторения в пакете; учёт всех сделок |
| Недоступные значения | Начальное состояние, нулевой объём и нулевой знаменатель дисбаланса |
| Точность | Суммы за пределами Number.MAX_SAFE_INTEGER; отсутствие промежуточного округления VWAP; округление половины цента |
| Настройки | Минимумы, максимумы, дроби, пустые и нечисловые значения |
| Apply | Нет изменений до Apply; сброс после Apply; одинаковые настройки; запуск после паузы |
| Управление | Pause отменяет генерацию; Resume сохраняет итоги; нет сделок за время паузы |
| Старые результаты | Snapshot, status, error и завершения загрузки старого запуска игнорируются |
| Навигация | Один производитель; сохранение показателей и running/paused |
| Ошибки | HTTP-ошибка, некорректный Wasm, несовместимый ABI, ошибка выполнения, Retry |
| Производительность | Учёт всех сделок при редких снимках; память Wasm не растёт с числом вызовов |
| Ресурсы | Завершение старого Worker, отмена таймеров, снятие обработчиков |

Генератор проверять через настоящий скомпилированный Wasm. Для времени и управления использовать fake timers и управляемые зависимости; длительные ожидания в реальном времени исключить. Оформление Material + Tailwind проверять в браузере на production-сборке.

## 5. Передача задач агентам и готовность продукта

Сначала выполнить этапы 1–2 и зафиксировать контракты. Затем распределять направления:

| Направление | Этапы | Зависимости |
|---|---|---|
| Генератор Wasm | 3 | ABI и рабочая загрузка |
| Расчёты и Worker | 4–5 | Контракты; для завершения этапа 5 нужен генератор |
| Angular-состояние и UI | 6–8 | Протокол Worker; ранняя разработка страниц на тестовых снимках |
| Интеграция и публикация | 9–10 | Завершённые предыдущие направления |

Агент интеграции отвечает за общие контракты, зависимости, конфигурацию Material/Tailwind и объединение изменений. Изменения ABI, протокола и правил оформления согласовывать до интеграции.

Каждый этап завершать осмысленным коммитом. Отчёт агента содержит реализованное поведение, выполненные проверки и ограничения. В готовом продукте генерация выполняется настоящим Wasm внутри Worker.

Продукт готов, когда:

- Все пять показателей соответствуют английскому ТЗ.
- Настройки, пауза, возобновление и навигация проходят обязательные сценарии.
- Старые результаты не изменяют новый запуск.
- Нет полной истории сделок и дублирующих производителей.
- Проверки проходят после чистой установки зависимостей.
- Максимальная конфигурация сохраняет работоспособность интерфейса.
- Material и Tailwind работают по согласованным правилам на desktop и mobile.
- Push в main автоматически обновляет проверенную демоверсию.
- README позволяет собрать проект и объясняет решения для собеседования.
